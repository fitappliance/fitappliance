# Architecture V3：Terra Max 执行协议

状态：执行协议已启用；实现状态只由原计划的进度表记录。修订日期：2026-09-14。

计划修订 PR 保持 docs-only。用户已授权按本协议在独立实现分支执行 G0–G11；
这不授权合并生产分支、发布数据或提升任何商品的 Fit 等级。

## 1. 权威顺序与目标

1. 用户已确认的业务、安全、存储与授权边界。
2. [Product Core Brief](../product-core-brief.md)：产品承诺和现有 Fit/lifecycle 契约。
3. [V3 原设计修订版](../superpowers/specs/2026-09-13-architecture-v3-evidence-foundation-design.md)：目标数据契约。
4. [V3 原执行计划修订版](../superpowers/plans/2026-09-13-architecture-v3-evidence-foundation.md)：任务、依赖、验收与唯一进度索引。
5. 本协议：分工、交接、审核、恢复和停机规则。

文档冲突不能由执行者静默选择。主 agent 先解释差异；常规实现细节由主 agent
在现有授权内裁决并同步原文。改变物理含义、证据门槛或产品承诺时，只暂停相关任务，
向用户提出一个最关键的决策问题：说明缺少什么证据、影响什么结果，以及需要选择的范围或授权。
不要让用户猜 PDF 尺寸，也不重复询问已经确认的 UNKNOWN/INSUFFICIENT_DATA 处理规则。

完成标准是可验证的证据链和安全消费，不是行数、覆盖率或测试数量本身。
优先复用现有模块；一个事实只有一个权威实现。不能通过删除反例、放宽门槛、
隐藏冲突、混淆尺寸筛选与 Verified Fit 来缩短代码或提高覆盖率。

2026-09-14 用户要求旧凭证补充信息、修复到与新凭证相同标准。旧原件继续保存，
但“旧规则仍可重放”不再是修复的终点：复用已验证证据，补齐真实缺口，再通过同一套
V3 验证、审核和仲裁生成新凭证。不得仅换版本号、重算哈希或给迁移对象开低门槛通道。
G1a 负责新版编码契约；单独的 G6c 负责补证迁移批次；G9b/G10 才负责受控消费切换。
升级完成、安装证据完整和 Verified Fit 仍是不同结论。

## 2. 固定分工

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 主 agent | 理解目标、任务拆分、输入版本、关键契约、风险判断、最终审核、进度记录、授权内提交/PR | 重做执行者已通过且输入未变的全部实现和测试 |
| 一个 GPT-5.6 Terra / Max 执行者 | 当前一个任务的局部实现、TDD、兼容性检查、证据整理、简短交接 | 自行改变业务规则、跳过依赖、合并发布、扩大写入范围、再委派 |

默认一个写入者。只有输入、输出和目录都独立且不共享可变状态时，才考虑并行；
不是为了并行而拆出第二个权威模块。G0–G11 的依赖不能用“同时启动”绕过。

通过当前会话的子 agent 接口创建执行者，不创建用户可见的独立任务来替代子任务。
主 agent 每次先确认工具实际支持以下设置，不静默换模型或降低推理档位：

```json
{
  "model": "gpt-5.6-terra",
  "reasoning_effort": "max",
  "fork_context": false,
  "message": "由主 agent 填入下文的一个完整、有限任务包"
}
```

任务包只包含相关背景、路径、输入版本和验收条件，不复制完整对话。
需要的技能由实际执行者亲自读取；实现者承担 TDD，主 agent 审查测试是否真的证明了目标。
执行者不得继续创建子 agent。当前任务结束后，由主 agent 决定复用或结束它，
下一个任务必须收到新的任务包，不能凭聊天记忆自行推进。

规格已经确定时，不重新启动整套架构设计。尽早保存可审核的小步产物；完整替换文档用单次
更新补丁，不先删除再长时间重建。篇幅目标不是通过门槛，格式错误局部修补，不为凑行数重写。
需要扩大调研或长时间没有可检查产物时，先交接现有结果和具体问题，由主 agent 收束范围。

## 3. 分支、文件与执行权限

- 计划 PR 保持 docs-only。实现从审核过的基础提交创建独立工作分支/工作树；
  不在主分支、计划工作树或有既存 recovery 改动的工作树中直接实现。
- 开始修改前核对远端、分支、GitHub 权限和工作树状态。记录事实，不输出 token、
  cookie、私密来源正文或凭据。
- 只修改任务包的文件白名单。需要额外路径时先解释原因，由主 agent 判定是否仍在
  当前任务范围内；用户业务授权有变化才向用户询问。
- 现有修改、原始 PDF、OCR 产物、receipt、ledger 和审核记录都不得删除或覆盖。
  不自动 stash/reset，不把整个 recovery 分支混入新实现。
- 代码、小型运行状态和正常构建留在项目规定的内部存储；大文件遵循外部 evidence
  store 配置。普通构建、测试和线上服务不能依赖外置盘挂载。
- 运行构建前检查副作用：现有完整 build 会重建公开产物。G0a 不运行这类写入命令；
  后续需要构建时在隔离工作树或明确的临时输出中运行，比较实际产物，并只提交任务允许的文件。
- 缺失外置盘时，普通便携检查继续；需要真实证据的 canary 记为 NOT_RUN/BLOCKED，
  保留上次结果，不能写入“空的成功结果”。
- 安装新 OCR 服务、付费调用、品牌外联、公开推送数据或生产发布都不是实现任务的默认权限。
  复用现有工具先完成可验证的最小链路。

## 4. 任务状态与唯一进度来源

```text
NOT_STARTED -> READY -> RUNNING -> REVIEW_REQUIRED -> COMPLETE
                         |                |
                         +---- BLOCKED ---+
```

- NOT_STARTED：尚未准备或派发；修订不重置已完成任务，新增任务从此状态开始。当前 24 个任务以原计划进度表为准。
- READY：主 agent 已验证所有前置任务、输入哈希和当前写入范围。
- RUNNING：任务包已交给唯一执行者，输入版本冻结。
- REVIEW_REQUIRED：执行者交付代码/文档与检查证据；它没有权力自行标 COMPLETE。
- COMPLETE：主 agent 审核与最终代码提交一致，必要检查和产物门禁已通过。
- BLOCKED：写清阻塞事实、受影响范围、保留的工作和恢复条件；不等于整个计划停止。

实现开始后，主 agent 在原计划的进度区记录每个任务的状态、审核提交、报告路径、
输入版本、遗留项、下一任务及理由。代码提交和后续进度记录提交可不同，但必须互相可追踪。
报告以版本化文档保存，例如 `docs/architecture-v3/execution/G0a-report.md`；该目录和报告
由对应实现任务建立，本次不创建“已执行”占位报告。

`.superpowers/sdd/` 已被忽略，可保存本地 brief、临时检查输出、审核反馈；
不能作为唯一续跑记忆，也不能保存原始私密证据。正式报告只记录允许公开的摘要、
对象哈希、已脱敏路径及当前检查结果。原始证据依照既有存储和权限政策保留。
任务结束后不自动删除工作树、报告或任何证据；清理需要单独满足用户的归档/校验要求。

## 5. 主 agent 每次派发的任务包

以下是填写规则，不是可不加修改地交给执行者的占位提示。
任务开始前所有必填项必须解析为当前真实值；未知产品事实则保留明确的未验证状态。

| 必填项 | 内容 |
| --- | --- |
| Task ID / 目标 | 原计划一个任务编号，以及一个可观察的完成结果 |
| 版本 | 工作树绝对路径、基础 commit、计划/spec 文件哈希、相关 policy 和 schema 版本 |
| 上游 | 已审核任务 commit、所需产物及哈希；外部证据另带可用性检查 |
| 必读 | Product Core Brief 的相关章节、原计划当前任务、spec 对应契约、现有生产者和消费者 |
| 写入白名单 | 精确文件；新增测试/fixture 的有限命名范围；禁止路径与产物 |
| 接口 | 必须导出的函数、参数、返回结构、错误/未知状态、兼容性约束 |
| 验收 | 正例、危险反例、重复操作/恢复条件、当前可运行的具体检查命令 |
| 不变边界 | identity/lifecycle/rights/Fit/原始证据/发布权限，以及任务特有约束 |
| 基准 | 相关公开产物/输入哈希、适用的 baseline，不混用 legacy 与 active release |
| 停机条件 | 需要主 agent 判断、需要用户新授权、输入变化、范围冲突的明确情形 |
| 交付格式 | 见下一节，必须区分已验证、未运行、失败和未知 |

可复用的任务说明：

> 你是本任务唯一执行者，模型 GPT-5.6 Terra，reasoning Max，不再委派。
> 只完成指定 Task ID；不要启动后续任务。先核对指定输入与工作树，读取相关技能。
> 复用现有代码，以最小改动满足当前任务的完整契约。实现行为变化时先写危险反例测试，
> 确认失败原因是目标行为；仅有模块不存在或语法错误不算反例验证。
> 只写白名单文件，保留所有既有改动和证据；不提交、push、合并、发布或改变 Fit 门槛。
> 遇到未知工程含义或范围冲突时保留候选和证据，只暂停依赖它的步骤并报告。
> 完成后按规定交接，不自行宣称下一阶段或全项目已完成。

主 agent 将填好的具体任务表附在该说明之后。若函数签名、文件或测试在当前版本不存在，
先区分“本任务要创建”与“声称已存在的上游”；后一种必须修正任务包，不能用 stub 冒充上游。

## 6. 执行者交接格式

交接正文保持简短，详细命令和输出索引放入当前任务报告。

```text
Task ID / status: Gxa / REVIEW_REQUIRED 或 BLOCKED
Base commit / current HEAD / diff identity:
Changed files:
Contract implemented:
Counterexample red -> green evidence:
Checks: command, exit status, tested input/code hash
Real canary: passed / failed / NOT_RUN, artifact and attestation identities
Public/lifecycle/rights impact:
Repeated batch / retry / resume / rollback evidence, if applicable:
Unresolved issues and exact scope:
Suggested next step, not executed:
```

`current HEAD` 不包含未提交 diff；未提交交付必须同时提供 diff 范围与校验，
主 agent 不能把旧 HEAD 的检查当成新改动的证明。主 agent 提交后记录最终 commit，
仅在文件内容、依赖、配置、输入或风险发生变化时补跑受影响检查。

每条失败必须如实说明，不能通过跳过测试、改断言为当前错误结果、修改旧证据或清空输出
制造绿色。估算“更短”“更快”不等于测得代码量、性能或 token 收益。

## 7. 主 agent 的审核门禁

主 agent 不逐行重复执行者的全部工作，但必须独立审核本次改动的关键证据：

1. **范围和契约：** diff 是否只实现当前任务，生产者与消费者是否对同一字段/状态有相同含义。
2. **危险反例：** 不同型号同 PDF、轴序/单位/配置混淆、缺失标注、null/false、未完成来源集等
   对应测试是否真的会失败；不要只看数量。
3. **完整链条：** source binding、Claim、receipt、review、eligibility、adjudication、snapshot
   是否各自证明正确的对象，不能用同一个 hash 或 accepted 字符串替代不同职责。
4. **有状态风险：** 重试、并发、崩溃恢复、第二批数据、撤回传播、缓存和回滚是否保留一致状态。
5. **发布边界：** 当前售卖与历史参考不串线，计算和凭证 UI 分开开启，未知不能留下旧 Verified Fit。
6. **检查真实性：** 确认实际测试覆盖新目录；独立 legacy oracle 未被新实现或 fixture 生成器污染；
   实盘证据 canary 与便携 fixture 检查没有互相冒充。

结构性失败、测试缺失或新发现的 source/rights/identity 风险必须在依赖继续前解决。
仅与当前契约无关、无数据/安全/发布影响的局部改进可列为非阻塞项，写清理由；
不能把未解决的核心问题改名为“后续优化”。

审核通过后主 agent 按现有授权提交、推送相应小 PR，并记录实际检查状态。
PR 检查绿色不等于已合并，合并不等于已部署；发布仍遵循现有门禁和独立授权。

## 8. 中断、压缩上下文与恢复

恢复时先读原计划进度区、当前任务报告和版本化契约，不从聊天摘要猜执行状态：

1. 核对工作树、HEAD、未提交文件和当前 Task ID，先保留全部已有内容。
2. 对照任务包的输入/上游/策略哈希；任何变化都标出影响范围。
3. 审核证据 ledger 的已提交 head/批次身份，不能用任务状态替代业务状态。
4. 重复操作沿用同一业务 idempotency key 和已提交事件；不得发明新键掩盖不确定结果。
5. 仅补跑因改变、失败或缺失证明而必要的检查，再恢复派发。

如果执行者中断，主 agent 先收集已写入的文件和可证明的检查，再决定继续同一执行者
或把精简恢复包交给新的 Terra / Max。不得让两个执行者同时修复同一状态。
分支更新或 rebase 后，检查记录必须绑定最终内容；先分析影响，不机械重做已证明且未变的工作。

## 9. 最初执行入口：G0a（已完成，保留历史）

完整文件白名单和验收以原计划 G0a 为准；主 agent 必须在派发时补齐当前实际值。

- **目标：** 冻结 active release 与 legacy 的独立基准，建立 dirty recovery 迁移清单，
  不修改业务代码或公开数据。
- **先读：** Product Core Brief、spec 第 2–4 节、原计划 G0a，以及当前发布描述符的真实消费者。
- **只读核对：** 主分支与工作树、远端权限、active pointer/descriptor、manifest、运行目录、
  来源和策略输入、当前测试覆盖、recovery 状态；对象不可用时记录为不可用。
- **必须区分：** legacy generated、active release、runtime、current-retail、historical/reference
  各自的 artifact identity、计数口径与 hash。不要把旧 3,521/3,515/3,513 数字硬编码成验收目标。
- **交付：** 基准、迁移映射、不可迁移或未核验项、无改动的公开产物证明及下一步输入。
- **不得执行：** build/sync/publish/recovery、OCR 重跑、安装新依赖、批量迁移、证据接受或删除。
- **完成门槛：** 主 agent 能据此准确指定 G0b 输入；存在未知来源并不允许猜测或宣称已修复。

后续按原计划顺序派发：先测试接线和语义，再 registry/文档解析、直接证据闭环，
之后有限家族派生、Fit shadow、既有发布链和最后 UI。任何 gate 的绿灯只证明该 gate，
不证明全目录已经具备完整安装证据。
